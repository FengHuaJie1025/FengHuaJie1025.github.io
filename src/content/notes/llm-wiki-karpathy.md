## 为什么需要 LLM Wiki

RAG 的工作流是：文档 → 分块 → 嵌入 → 检索 → 生成。看起来很完善，但核心缺陷在于——知识状态是无状态的（stateless）。每一次查询都是一次全新的检索+生成，上一个问题的分析结果不会沉淀下来。

2026 年 4 月，Andrej Karpathy 在 GitHub Gist 上发布了 **LLM Wiki** 模式。它不替代 RAG，而是提出了一种不同的知识组织哲学：**把知识「编译」好，而不是每次「解释」一遍。**

## RAG vs LLM Wiki

| 维度 | RAG（向量检索） | LLM Wiki |
|------|---------------|----------|
| 知识状态 | 无状态，每次重新检索 | 持久化，已编译，持续积累 |
| 检索可靠性 | 依赖分块质量、Top-K 等参数 | ~100%（全量在上下文窗口内） |
| 多文档综合 | 每次从碎片拼凑 | 交叉引用在摄入时预建 |
| 矛盾检测 | 不可能 | 编译阶段标记并处理 |
| 基础设施 | 向量数据库 + 嵌入管道 | 一个文件夹 + 任意编码 Agent |

Karpathy 的原话：「RAG 用技术复杂度换取内容量。LLM Wiki 用前期精炼换取查询时的简单与准确。」它们不是替代关系。**稳定的精选知识编译成 Wiki（L1 缓存），动态/海量/高频变化的数据用 RAG（L2 缓存）。** 混合模式才是终局。

## 三层架构

### Layer 1：Raw Sources（源材料层）

位置：`raw/`。存放所有源文件——PDF、文章、网页剪藏、论文。核心原则：**LLM 只读不写。** 这是整座知识大厦的事实源头，每一条 Wiki 陈述最终都可追溯至此。

### Layer 2：The Wiki（编译层）

位置：`wiki/`。LLM 从原始材料中提炼、组织、撰写的一系列 Markdown 文件。页面类型包括概念页、实体页、摘要页、矛盾标记、交叉引用和综合页面。

在 5 万-10 万 tokens 以内，LLM 可以一次性加载整个 Wiki 到上下文窗口，检索召回率接近 100%。这比任何向量检索都更快、更准。

### Layer 3：Schema（规则层）

位置：`CLAUDE.md`。Wiki 的编辑风格手册，告诉 LLM 按什么规范来维护 Wiki。这是整个模式最容易被忽视但最关键的组件——没有 Schema 的 Wiki 会在几轮摄入后出现命名不一致、交叉引用断裂、页面结构漂移。

## 三个核心操作

**Ingest（摄入）**：向 `raw/` 添加新文档后，LLM 自动全文阅读、创建/更新摘要页、提取实体和概念、建立交叉引用、更新索引和日志。一次性 token 成本，换来永久的结构化收益。

**Query（查询）**：加载 `index.md`（~2000 tokens）→ 定位 2-4 个相关页面（~1000-2000 tokens）→ 综合生成答案。好的答案可以归档回 Wiki 成为新页面。

**Lint（审计）**：周期性运行，扫描跨页面矛盾、过时声明、孤立页面、断裂的 wiki-link 和知识盲区。Lint 后还会建议下一步应该研究什么——知识库具备了自我诊断和增长规划能力。

## 15 分钟搭建

```bash
mkdir -p my-wiki/{raw,wiki}
touch my-wiki/wiki/index.md
touch my-wiki/wiki/log.md
touch my-wiki/CLAUDE.md
```

将第一篇论文放入 `raw/`，然后在 Claude Code 中执行一条摄入命令，LLM 将自动创建 3-8 个新页面并建立完整的交叉引用网络。

## 规模天花板

| 规模 | 策略 |
|------|------|
| < 5 万 tokens | 纯 Wiki，全量加载到上下文 |
| 5 万-20 万 tokens | Wiki 索引 + 选择性页面加载 |
| > 20 万 tokens | Wiki + 语义搜索混合 |

Karpathy 的贡献不在于发明了新工具，而在于划清了这条线：**LLM 负责记账，人类负责思考。** 这个分工，就是整个模式的全部意义。
