## 上下文工程

每次你和 LLM 对话，它看到的不是当前这一句话——而是从第一条消息开始的所有文字，加上你的系统提示词、工具定义、对话历史。这些全部打包成 Token 发给模型。

Token 是有价格的。

以 OpenAI 为例（2026 年价格）：

| 模型 | 输入价格 (每 1M Token) | 输出价格 (每 1M Token) |
|------|---------------------|---------------------|
| GPT-4o | $2.50 | $10.00 |
| GPT-4o-mini | $0.15 | $0.60 |
| Claude Sonnet 4 | $3.00 | $15.00 |
| DeepSeek-V3 | $0.14 | $0.28 |

这意味着什么？一个 20000 Token 的上下文 + 500 Token 的输出，用 GPT-4o 成本约 **$0.55**，用 Claude Sonnet 4 约 **$0.73**——差 33%。如果日活 10 万用户，每月成本差 **$5000+**。

更关键的是：**上下文越长，延迟越高，成本越高，但质量不一定更好。**

上下文工程（Context Engineering）就是研究如何在有限的上下文窗口内，用最合理的方式组织信息，让模型在质量和成本之间取得最优平衡。

## 上下文窗口的演进

| 时期 | 窗口大小 | 代表模型 |
|------|---------|---------|
| 2022-2023 | 4K-8K | GPT-3.5, Claude 2 |
| 2024 | 128K | GPT-4 Turbo, Claude 3, Qwen2 |
| 2025 | 200K | Claude 3.5 Sonnet, Gemini 1.5 |
| 2026 | 1M+ | Claude Opus 4.8 [1M], DeepSeek-V3.1 |

窗口越来越大，但**用满窗口不等于用得好**。128K 的窗口意味着你可以一次性塞进一本电子书，但模型真正有效利用的可能只有前 20K。

## 一、上下文的经济账：什么时候该长，什么时候该短

### 长上下文的优势

- 不需要 RAG 等外部检索，一次拿到完整上下文
- 可以处理需要综合多处信息的复杂任务
- 减少 API 调用次数（一次长对话代替多次短对话）

### 长上下文的劣势

- **成本线性增长**：128K 比 4K 贵 32 倍
- **延迟增加**：Token 越多，生成越慢
- **注意力稀释**：模型在长文本中容易"丢失"关键信息（needle in a haystack 问题）
- **幻觉风险上升**：信息越多，模型混淆的可能性越大

### 决策树

```
用户发来了一个新问题
  │
  ├─ 需要领域知识吗？
  │    ├─ 不需要 → 短上下文（只带系统提示 + 当前问题）
  │    └─ 需要 → 进入下一步
  │
  ├─ 知识能稳定 RAG 检索到吗？
  │    ├─ 能 → RAG + 短上下文（最佳性价比）
  │    └─ 不能 → 进入下一步
  │
  ├─ 需要综合多处信息推理吗？
  │    ├─ 不需要 → 短上下文 + 直接 Prompt
  │    └─ 需要 → 长上下文（接受成本代价）
  │
  └─ 信息是实时变化的吗？
       ├─ 是 → RAG（避免模型记住过时信息）
       └─ 否 → 长上下文一次性加载
```

## 二、上下文压缩策略

### 1. 历史对话摘要

对话越长，历史消息占用越多 Token。对早期对话进行压缩摘要，是最高效的压缩手段。

```python
def compress_history(messages: list[dict], target_tokens: int = 2000) -> list[dict]:
    """把早期对话压缩为摘要，保留最近的对话作为完整上下文"""
    if len(messages) <= 4:
        return messages  # 对话很短，不需要压缩

    # 保留最近 2 轮完整对话
    recent = messages[-4:]

    # 把更早的部分压缩成一条摘要
    old_messages = messages[:-4]
    summary_prompt = f"""
请总结以下对话的关键内容，保留所有重要信息和决策点，控制在 200 字以内。
用第三人称叙述，包含：讨论的主题、达成的结论、待办事项。

对话：
{format_messages(old_messages)}
"""
    summary = llm.generate(summary_prompt)

    # 重组
    return [
        {"role": "system", "content": f"[历史对话摘要]\n{summary}"},
        *recent
    ]
```

**效果**：把 50 轮对话（~15K Token）压缩为摘要 + 最近 2 轮（~3K Token），节省 80% 的上下文 Token。

### 2. 选择性保留

不是所有历史消息都有同等价值。按重要性分层处理：

| 层级 | 内容 | 处理方式 |
|------|------|---------|
| **系统提示** | 角色定义、任务说明 | 始终保留（高质量信息） |
| **最近 3-5 轮** | 当前任务相关对话 | 完整保留 |
| **近期摘要** | 5-20 轮前的对话 | 压缩为段落摘要 |
| **早期对话** | 20 轮以上 | 压缩为单句摘要或直接丢弃 |

### 3. Token 预算控制

给每轮对话设置 Token 预算上限，超出则触发压缩：

```python
MAX_CONTEXT_TOKENS = 8000  # 硬上限

def trim_to_budget(messages: list[dict], budget: int = MAX_CONTEXT_TOKENS) -> list[dict]:
    """从最早的对话开始裁剪，直到总量在预算内"""
    token_counter = count_tokens(messages)
    if token_counter <= budget:
        return messages

    # 从最早的非系统消息开始裁剪
    trimmed = [messages[0]]  # 保留 system prompt
    for msg in reversed(messages[1:]):
        trimmed.insert(1, msg)
        token_counter = count_tokens(trimmed)
        if token_counter <= budget:
            break

    return trimmed
```

### 4. 滑动窗口 + 关键信息保留

最简单但有效的策略：只保留最近的 N 轮对话，丢弃更早的。

```python
# 保留最近 6 轮（12 条消息：6 user + 6 assistant）
WINDOW_SIZE = 12

def sliding_window(messages: list[dict]) -> list[dict]:
    return messages[-WINDOW_SIZE:]
```

**适用场景**：多轮对话中早期内容与当前问题无关的情况。
**不适用**：需要上下文推理的任务（如代码调试，早期报错信息可能很关键）。

## 三、上下文结构设计

### 信息排列顺序的影响

LLM 对上下文中的信息有不同的"注意力权重"：

```
高注意力区：          系统提示词、最近 3-5 条对话
                    （模型最可能记住和引用）

中注意力区：          中间 10-20 轮对话
                    （部分保留，可能遗忘细节）

低注意力区：          最早的历史对话
                    （容易被忽略或"遗忘"）
```

**最佳实践：把最重要的信息放在上下文的两端**

```
开头（系统提示，始终在窗口内）：
├── 角色定义
├── 任务目标
├── 输出格式要求
└── 关键约束条件

中间（对话历史）：
├── 最近 3-5 轮完整对话
└── 早期对话的摘要

结尾（最近的消息，模型最后看到的）：
├── 用户最新问题
└── 最近一次助手回复
```

### 示例：客服对话的上下文组织

```yaml
# 系统提示（约 500 tokens）
role: 客服代表
style: 友好但专业
knowledge_base: 产品 FAQ + 退货政策
constraint: 不承诺超出权限的事，涉及退款必须转人工

# 最近 3 轮完整对话（约 600 tokens）
user: 我的订单 ORD-001 三天了还没发货
assistant: 我来帮您查询订单状态...

# 早期对话摘要（约 200 tokens）
[摘要] 用户 30 分钟前咨询了产品功能问题，已解答。
        用户今天有 3 条未解决工单：ORD-001（发货）、ORD-002（退货）、ORD-003（发票）。

# 当前问题（约 50 tokens）
user: 我刚才说的 ORD-002 退货怎么还没处理？
```

总上下文约 1350 tokens，而如果把 30 分钟前的完整对话也保留，可能需要 3000+ tokens，但实际有用的信息没有翻倍。

## 四、RAG 与上下文工程的关系

RAG 和上下文工程不是对立关系，而是互补的：

```
RAG 解决"模型不知道什么"的问题
上下文工程解决"怎么高效地告诉模型已知信息"的问题
```

### 混合策略

```
用户问题
  │
  ▼
RAG 检索最相关的 3-5 个片段（约 1000-2000 tokens）
  │
  ▼
系统提示词（约 500 tokens）
  │
  ▼
最近 3 轮对话历史（约 600 tokens）
  │
  ▼
总计约 2500 tokens → 发给模型
```

这样总上下文控制在 3000 tokens 以内，而 RAG 确保模型获得了必要的领域知识。

### 检索内容的排序

RAG 检索回来的片段，如何放入上下文也有讲究：

```
错误做法：直接把检索结果拼在问题后面
正确做法：按相关度排序，最相关的放在最前面（靠近用户问题）

上下文结构：
[系统提示]
[对话摘要 - 如有]
[RAG 片段 1 - 最相关]
[RAG 片段 2]
[RAG 片段 3]
[用户当前问题]
```

模型对"靠近问题"的信息关注度更高，所以把最相关的检索结果放在最后（靠近问题）。

## 五、长上下文模型的利用技巧

### 128K+ 窗口的正确使用姿势

长上下文窗口不是用来"塞更多东西"的，而是用来做**需要全局视野**的任务：

| 适合长上下文的任务 | 原因 |
|-----------------|------|
| 整代码库搜索和修改 | 需要看到文件间关系 |
| 长文档分析和总结 | 信息分布在文档各处 |
| 多文件重构 | 需要了解全局结构 |
| 法律文书分析 | 条款间交叉引用 |

| 不适合长上下文的任务 | 原因 |
|-------------------|------|
| 简单问答 | RAG + 短上下文更划算 |
| 单文件代码修改 | 只加载相关文件即可 |
| 实时对话客服 | Token 成本太高，ROI 低 |

### 长上下文的陷阱

**1. 注意力稀释（Loss in the Middle）**

模型对长上下文中间部分的信息注意力最低：

```
位置:  [开头] ... [中间 50K tokens] ... [结尾]
注意力: [高]              [低]               [高]
```

解决方案：把最关键的信息放在开头或结尾，不要指望模型从长文本中间找到信息。

**2. 幻觉放大**

上下文越长，模型混淆不同段落信息的可能性越高。

解决方案：对长上下文中的关键事实进行验证，或拆分为多个短上下文分别处理后再汇总。

**3. 成本失控**

一次 100K Token 的输入 + 5K Token 的输出，用 GPT-4o 成本约 $0.30，如果用 GPT-4o-mini 只需 $0.02。同样的任务，选错模型差 15 倍。

## 六、上下文工程的最佳实践清单

### 设计阶段

- [ ] 明确每个功能的上下文预算（最大 Token 数）
- [ ] 决定哪些知识走 RAG，哪些走上下文直接加载
- [ ] 设计系统提示词模板，控制在 500-1000 tokens 以内
- [ ] 定义对话历史的保留策略（滑动窗口 vs 摘要 vs 混合）

### 开发阶段

- [ ] 实现 Token 计数工具（`tiktoken` 或 `langchain`）
- [ ] 实现上下文自动压缩逻辑
- [ ] 实现 RAG 检索结果的排序和截断
- [ ] 设置 Token 预算超限的熔断机制

### 运行阶段

- [ ] 监控每次请求的 Token 消耗（输入/输出分别统计）
- [ ] 跟踪上下文大小分布（P50/P95/P99）
- [ ] 对比不同压缩策略的效果（A/B 测试）
- [ ] 定期审查系统提示词，移除过时或冗余内容

### 性能优化 Checklist

```
当前每次对话平均上下文: 8500 tokens
├── 系统提示词:  500 tokens  ✓ 已精简
├── RAG 检索:    2000 tokens ✓ 3 个片段，已按相关度排序
├── 对话历史:    4500 tokens ✗ 可以压缩到 2000 tokens
├── 当前问题:     100 tokens  ✓
└── 额外开销:    1400 tokens ✗ 检查是否有重复信息

优化后预计: 8500 → 6000 tokens，成本降低 29%
```

## 七、常见场景的上下文方案

### 场景 1：客服机器人

```
上下文构成：
├── 系统提示（角色、话术规范）：500 tokens
├── 最近 3 轮完整对话：600 tokens
├── 用户画像摘要（从 DB 查）：300 tokens
├── RAG 检索产品知识：1000 tokens
└── 当前问题：50 tokens
总计：约 2450 tokens
```

### 场景 2：代码助手

```
上下文构成：
├── 系统提示（代码规范）：300 tokens
├── 相关文件内容（3-5 个文件）：3000-8000 tokens
├── 最近对话历史：500 tokens
└── 当前问题：100 tokens
总计：约 4000-9000 tokens
```

### 场景 3：文档分析助手

```
上下文构成：
├── 系统提示：200 tokens
├── 文档全文（< 128K 的 PDF/Word）：50000-100000 tokens
└── 当前问题：100 tokens
总计：约 50000-100000 tokens
→ 适合用长上下文模型，但注意成本和延迟
```

### 场景 4：多轮对话记忆

```
策略：分层记忆
├── 当前会话（最近 6 轮）：完整保留，约 1200 tokens
├── 本周记忆（摘要）：压缩为 300 tokens
├── 上月记忆（概要）：压缩为 100 tokens
└── 更早：丢弃或向量检索
总计：约 1600 tokens，跨会话保持记忆
```

## 总结

上下文工程的核心思想：**信息的质量比数量重要，信息的排列比总量重要，信息的时效性比历史长度重要。**

- 能用 RAG 的不要用长上下文（成本低、知识新）
- 必须用长上下文的，做好分层压缩（历史摘要 + 近期完整）
- 永远把最重要的信息放在上下文的开头和结尾
- 每次请求后监控 Token 消耗，找出可以优化的地方
- 选对模型：简单任务用便宜的小模型，复杂推理才用大模型

最好的上下文策略不是塞满整个窗口，而是让模型只看到它需要的东西——不多不少。
