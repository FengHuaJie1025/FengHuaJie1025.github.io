## AI 到底能帮你什么？

- **快速生成骨架代码**：API 路由、数据模型、DTO、测试脚手架，这些有固定模式又不得不写的代码
- **解释陌生代码**：接手遗留项目时，把一段晦涩的逻辑丢给 AI，几分钟拿到清晰的解释
- **辅助调试**：把报错日志和上下文丢过去，AI 可以缩小排查范围
- **写重复测试**：围绕一个函数生成单元测试和边界案例，省掉大部分机械劳动
- **信息检索**：翻文档、找 API 用法，比搜索引擎+手动筛选快得多

同时也要知道 AI 的边界：**它不懂你的业务，不理解你的架构决策背后的权衡，不会替你思考"该不该这么做"。** 提效的关键不是让 AI 替你写代码，而是用它把你从机械劳动中解放出来，让你把精力放在真正需要判断的事情上。

## 一、编程：让 AI 帮你写"不得不写"的代码

### 1.1 骨架与胶水代码

项目中总有一些写起来烦、不写又过不去的东西：

- 一个数据模型 + 对应的增删改查 API
- 一个 DTO + 转换器
- 一个 Controller + Service + Repository 三层调用链
- 一个配置文件解析器

这些代码有固定的模式，写一遍两遍还好，写到第五遍就是纯粹的体力活。把你的需求说清楚，AI 能一次性生成完整的一套。

**推荐做法**：用 AI 生成第一版，然后你 review 和修改。不要指望一次性完美——AI 生成的结构大概率是对的，但命名风格、异常处理细节、业务约束需要你来把关。

### 1.2 跨语言/跨框架迁移

从 Java 转到 Kotlin、从 JavaScript 转到 TypeScript、从 Spring 转到 Micronaut——这种迁移工作重复性极高，逻辑相同，只是语法和框架 API 不同。AI 接这种活比人快得多。

实践中：分段迁移，每次给出一个文件或一个模块的原文，让 AI 输出目标语言/框架的版本，然后逐段 review。

### 1.3 正则与数据处理脚本

正则表达式是多数程序员的痛点。与其花半小时自己拼写和调试，不如直接描述你要匹配的内容，让 AI 生成正则并附带测试案例。同样适用于各种数据处理脚本（JSON 转换、CSV 清洗、日志解析）。

## 二、调试：把 AI 当成结对调试伙伴

### 2.1 快速定位问题范围

碰到一个诡异的 bug，常规做法是逐行看代码猜原因。现在可以这么做：

1. 把报错信息和相关代码片段丢给 AI
2. 让它列出最可能的原因，按概率排序
3. 对照它的排查方向，你去做验证

这里的关键技巧：**不要只给报错信息**。AI 需要上下文——相关的代码、输入数据、你期望的行为和实际行为。给的上下文越充分，它的诊断越准。

### 2.2 解释难以理解的逻辑

接手一段没有注释、变量名只有三个字母、逻辑绕了三层的老代码时，与其一个人对着屏幕头疼，不如把代码贴给 AI 让它逐段解释。

可以用固定的指令格式：

> 解释以下代码的逻辑，按执行顺序拆解。每段用中文描述它在做什么，以及可能存在的问题。

### 2.3 安全检查

AI 在发现常见安全隐患上很擅长：SQL 注入、XSS、硬编码密码、缺失的输入校验、不安全的反序列化。写完代码后交给 AI 做一轮安全 review，成本极低，收益稳定。

## 三、文档与知识管理：AI 是最好的"写手"

### 3.1 从代码生成文档

写了函数，需要生成 Javadoc/KDoc/TSDoc 注释？写完一个模块，需要写 README？这些都适合交给 AI。原则：代码是你的，文档让它写。

### 3.2 写技术方案文档

写设计文档的时候，很多人对着空白页面发愁。换个方式：把你的思路用口语化的方式说出来（可以是语音转文字，也可以直接打字），让 AI 帮你整理成结构化的文档。

比如你说了七八条散乱的想法，让它以"背景-方案-选型理由-风险"的结构重组。你在重组后的版本上修改，比从零开始写快得多。

### 3.3 代码 Review 总结

做完一次 Code Review，让 AI 帮你整理要点并按严重程度分类。Review 意见是你的，格式整理和归类让它做。

## 四、学习：用 AI 加速技术吸收

### 4.1 快速上手陌生技术栈

遇到一个新框架、新库、新协议，与其从头翻一遍官方文档，不如直接问 AI：

> 我要在 Spring Boot 3 里集成 RabbitMQ，实现一个延迟队列。请按步骤告诉我需要做什么，每一步给出代码示例和配置。

AI 会直接给你可用的答案，不用在一整篇文档里自己捞重点。等跑通了，再回头去读文档深入细节。

### 4.2 "一页速查表"

学新东西时，让 AI 帮你生成一页速查表，包含最常用的命令/API/概念。打印出来贴桌上，比每次翻文档快得多。

### 4.3 追问式学习

看一段代码或文档有不懂的地方，直接追问 AI，不用自己串上下文。就像有一个随时在线的技术导师，不懂就问，问到懂为止。

## 五、架构设计：AI 是讨论对手，不是决策者

### 5.1 方案选型的辅助分析

在几个方案之间纠结时，可以让 AI 帮你列出对比维度：性能、维护成本、学习曲线、社区活跃度、生态兼容性。它不会替你做决定，但它能帮你把信息组织得更清晰。

### 5.2 发现盲区

你做了一个技术决策，让 AI 尝试反驳你。这是一种很有用的"红队演练"——AI 可能会指出你没考虑到的边界情况、性能瓶颈或者运维复杂性。不需要全盘接受它的意见，但它能帮你补漏。

### 5.3 API 设计建议

设计 REST API 或接口时，让 AI 基于你的需求给出设计草案，你再根据业务语义调整。AI 擅长保持风格一致（URL 命名规范、请求响应结构对称），人负责判断语义是否合理。

## 六、自动化：把重复劳动交给 AI

### 6.1 批量代码修改

重构时经常遇到这样的场景：把项目中所有 `Date` 换成 `LocalDateTime`，或是把所有 `@GetMapping` 改成统一的 API 前缀。这种工作是 AI 的强项——它能在整个项目范围内做模式匹配和替换。

关键：**改完后一定要 review diff**。AI 的模式匹配不是 100% 可靠的，边界情况（注释里的引用、字符串里的日期格式）可能被误改。

### 6.2 Git 提交信息

写了半天代码，到提交的时候不知道 commit message 怎么写。让 AI 看 diff 帮你生成一个规范的提交信息，你确认后直接用。

### 6.3 PR 描述

类似地，把 PR 的变更内容交给 AI，让它按规范的格式生成 PR 描述：变更动机、改动范围、测试情况、风险说明。

## 几个通用的效率习惯

**1. 维护自己的提示词模板库**

把常用的提示词存下来，分场景整理。你会发现高频率场景就那么十几种——调试、写测试、写文档、代码解释、架构分析、代码迁移——每种场景积累 2-3 个提示词模板，每次直接套用即可。

**2. 上下文越全，输出越好**

很多人抱怨 AI 答案质量低，但检查一下自己的输入：只给了半句话、没有背景信息、没有例子、没有约束条件。AI 不是读心术，你给它什么它就还你什么。提供完整的上下文，是最简单的提效手段。

**3. 不要把 AI 的输出当最终结果**

AI 生成的东西永远是草稿。把它当成一个能力很强但不靠谱的初级工程师——他干活快，但你得 review。每一条 AI 生成的代码都要经过你的确认，这个环节不能省。

**4. 理解工具的边界**

不同 AI 工具擅长不同的事：Claude Code 适合复杂任务编排和深度推理，Cursor 适合日常编码，Copilot 适合快速补全。选对工具，比学会所有工具重要得多。

## 总结

AI 不会替代程序员，但会用 AI 的程序员会替代不会用的。这个判断在今天已经不是预言，而是正在发生的事实。

提效的核心不在于找到"最好的 AI 工具"，而在于**分辨哪些工作是可以交给 AI 的机械劳动，哪些必须由你来做判断**。把重复的、有固定模式的、不需要业务决策的事情交给 AI，把精力集中在架构决策、业务理解、代码质量把控上——这才是 AI 时代的程序员效率之道。
