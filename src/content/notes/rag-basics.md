## 什么是 RAG

RAG（Retrieval-Augmented Generation）让大模型先"查资料"再生成答案，缓解幻觉、引入私有知识。核心思路：模型不依赖自己的参数记忆，而是从外部知识库中检索相关片段作为上下文，再基于这些片段生成回答。

## 为什么需要 RAG

大模型的知识截止于训练数据的时间点，且无法覆盖企业的私有文档、个人资料或最新的实时信息。如果没有 RAG，模型只能靠参数记住的内容回答，容易产生幻觉或给出过时信息。RAG 解决的问题：让模型拥有"翻书"的能力，而不是全靠"脑子记"。

## 完整链路

### 1. 切分（Chunking）

把原始文档切成语义完整的片段。切分策略直接影响检索质量。

**常见方法：**

- **固定长度切分**：按 Token 数切（如 256/512 tokens），简单但容易切断语义
- **递归字符切分**：按段落→句子→子句逐级切分，尽量保持语义完整（LangChain 的 RecursiveCharacterTextSplitter）
- **语义切分**：利用 embedding 检测语义边界（如句向量突变处），效果最好但成本高
- **特定格式切分**：Markdown 按标题层级切、代码按函数/类切、HTML 按标签结构切

**关键参数：**

- **chunk size**：片段大小。太小则丢失上下文，太大则引入噪声，检索精度下降
- **chunk overlap**：片段之间的重叠字数（通常 10%-20%），避免关键信息恰好落在切分边界上
- 中文场景建议 300-500 字 + 10% overlap

### 2. 向量化（Embedding）

把文本片段转换成向量（一串浮点数），让计算机能计算语义相似度。

**中文友好的 embedding 模型：**

| 模型 | 维度 | 说明 |
|:---|:---|:---|
| BAAI/bge-large-zh-v1.5 | 1024 | 国产最强中文 embedding，BGE 系列，MTEB 中文榜前列 |
| text-embedding-3-small | 1536 | OpenAI，中文尚可但需梯子 |
| m3e-base | 768 | Moka 开源，轻量中文友好 |

"检索"在向量数据库里就是做**相似度计算**，常用距离度量：

- **余弦相似度（Cosine Similarity）**：最常用，只看方向不看长度
- **点积（Dot Product）**：适用于归一化后的向量
- **欧氏距离（Euclidean Distance）**：少用，对向量尺度敏感

### 3. 检索（Retrieval）

将用户问题向量化后，在知识库中找到最相似的 K 个片段。

**检索方式：**

- **向量检索**：语义检索，能召回"意思相近但字面不同"的内容
- **关键词检索（BM25）**：传统方法，精确匹配关键词，适合人名/编号/专有名词
- **混合检索（Hybrid Search）**：向量 + BM25 加权融合，效果通常最好
- **Rerank 重排**：用专门的排序模型对 top-K 结果再精排

### 4. 重排（Rerank）

向量检索的 top-K 结果中，排在前面不一定是最相关的。重排用更精细的交叉编码器（Cross-Encoder）对候选片段逐一打分，重新排序。

**为什么需要重排：** 向量检索是"粗略匹配"，速度快但精度有限；重排是"精细判断"，慢但准确。两段式设计兼顾效率与精度。

**常用重排模型：**

- BAAI/bge-reranker-v2-m3
- Cohere Rerank
- Jina Reranker

### 5. 生成（Generation）

把检索到的片段拼接进 prompt，让 LLM 生成带引用的答案。

**Prompt 模板结构：**

```
你是一个知识问答助手。请基于以下参考资料回答用户问题。
如果参考资料不足以回答问题，请明确说明"知识库中未收录相关内容"。

参考资料：
[1] (来自 xxx.pdf)
[2] (来自 xxx.md)

问题：{user_question}
回答：
```

在 prompt 中要求模型标注引用来源（如 `[1]`、`[2]`），方便用户核实信息。

## 召回率优化策略

### 检索前优化

- **查询改写（Query Rewriting）**：把用户模糊问题改得更精确，如"杭州的天气"→"杭州2026年8月的天气"
- **查询扩展（Query Expansion）**：用 LLM 生成问题的多个变体，分别检索后合并结果
- **HyDE（Hypothetical Document Embeddings）**：先让 LLM 生成一段假设性的理想答案，再用这段答案去检索

### 检索后优化

- **多路召回**：同时用向量检索 + BM25 + 其他方式，合并去重
- **滑动窗口**：返回连续片段时，额外返回相邻片段补全上下文
- **重排**：精排提升准确率
- **去重与过滤**：去除冗余或低分片段

### 知识库优化

- **chunk 粒度调优**：根据文档类型调整大小
- **元数据过滤**：给每篇文档打标签，检索时先过滤范围（如只查"技术文档"类）
- **定期更新索引**：增量更新 vs 全量重建

## 评估体系

### 检索质量

- **召回率（Recall）**：正确答案是否在返回结果中
- **精确率（Precision）**：返回结果中有多少是相关的
- **MRR（Mean Reciprocal Rank）**：第一个正确答案排在第几位

### 生成质量

- **忠实度（Faithfulness）**：答案是否基于检索结果，不编造
- **相关性（Relevance）**：答案是否回答了用户问题
- **完整性（Completeness）**：是否遗漏重要信息

### 评测工具

- **RAGAS**：专门评估 RAG 系统的开源框架
- **TruLens**：带反馈函数的评估工具
- 人工评测：构造测试集，逐条打分

## 常见架构模式

### 朴素 RAG

最简单的"检索 → 拼接 → 生成"模式。适合知识库小、问题简单。

### 高级 RAG

在检索前后增加优化步骤（查询改写、重排、多轮检索等）。适合多数生产场景。

### 模块化 RAG

将各环节模块化，可灵活替换和组合。适合需要深度定制的场景。

### Agentic RAG

引入 Agent 自主决定：是否需要检索、用什么工具检索、多次检索还是单次、如何推理答案。适合复杂问题场景。

### Self-RAG

让模型在生成过程中自我反思并判断引用是否可靠。适合对准确性要求极高的场景。

## 中文场景的坑

- **用英文 embedding 模型处理中文** → 语义偏移严重。必须用中文训练/微调的 embedding 模型
- **分块太大** → 一个 chunk 包含多个主题，检索精度下降
- **分块太小** → 丢失上下文，模型看不懂
- **中文不按空格分词** → 切分策略要考虑标点断句和语义边界，不能直接照搬英文的按词切分
- **中文检索词与原文字面差异大** → 只靠关键词搜索效果差，必须用语义检索
- **简体/繁体混用** → embedding 模型表现不一，尽量统一用语

## 实战建议

1. **起步先用朴素 RAG**，跑通链路后再逐步加优化
2. **chunk 策略从 300-500 字 + 10% overlap** 开始调
3. **混合检索（向量 + BM25）通常优于单一检索方式**
4. **必须加重排**，对精度提升明显
5. **prompt 中要求标注引用来源**，方便排查幻觉
6. **建立评估测试集**，每次改动都跑一遍评测，避免盲目优化
